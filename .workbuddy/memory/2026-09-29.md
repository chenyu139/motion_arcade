## 头部识别管线深度优化（本轮主要工作）

### 1. 自适应滤波 `core/filters.py`（新增）
- **One Euro Filter** 替换固定时间常数低通（yaw/axis 两路）：静止按 `min_cutoff` 重滤波锁噪声，移动时按速度抬高截止频率减少滞后。`beta=0` 与原来的固定低通严格等价（可回退）。
- **踩坑 1**：直接上 One Euro 会让单帧误检尖峰因"瞬时速度极大"把截止顶到几乎直通 —— 孤立尖峰峰值从严格的 0 涨到 0.067、两帧尖峰到 0.40，绕过所有后续门限。
- **解法是两层，缺一不可**：
  - ① `RateLimiter` 运动学速率上限（`YAW_MAX_RATE=5.0`，依据 yaw≈2.14·sin(θ)，快速转头约 4.6/秒）。**必须放在 One Euro 之前**，顺序反了就失效。
  - ② 速度死区 `YAW_EURO_SPEED_DEAD=2.5`（噪声也有速度，低于它的按静止处理 → 截止恒等于 min_cutoff）。

### 2. 人脸检测后端 `core/tracker.py`
- `IlluminationGuard`：暗/过曝/低对比才做 gamma + CLAHE，带 24 帧迟滞；**只增强人脸检测那一路**（`ILLUM_FACE_ONLY`），不碰手部肤色阈值。
  - **踩坑 2**：gamma 指数方向搞反 —— 写成 `x^(1/γ)` 让暗画面更暗（38→35），正确是 `x^γ`（γ<1 提亮）。修正后 38→84。
  - `ILLUM_LOW_CONTRAST_T` 从 42 下调到 30：真实室内画面 std 多落在 40~70，42 会把正常画面误判为低对比。
- `FaceTargetSelector`：多人目标"所有权"。① 面积达 1.8 倍才允许接管（没有这条会被连续性永久死锁）；② 遮挡后回归按连续性**立即**认回，不走防抢夺迟滞；③ 记位置不记下标（候选顺序在 cv2 里不稳定）。
- 启用 YuNet 置信度 `f[14]`（`FACE_MIN_SCORE=0.55`），`_face_score` 防御式取值：列数不足/NaN 一律降级为 1.0 —— **失败方向必须是"少一层过滤"，不能是"整个后端失效"**。

### 3. 质量评估与降级 `inputs.py` + `config.py`
- `HeadController._assess` 分级 `good/far/poor/angle/lost`，迟滞方向刻意为 **变差快(0.7s)、恢复慢(1.6s)** —— 同方向用同一时长会让提示在边界来回闪。
- 唯一改行为的降级：`poor/lost` 时不再接受**新的**动作键触发（误跳是体感最糟的失败）；已按住的不受影响；`far` 只提示不禁用。

## 手部始终检测不到（用户反馈，已修）

三个根因，都已在 `core/tracker.py` / `core/config.py` 修掉：

1. **送检分辨率错配（主因）**：骨骼/手部 21 点被喂 `small`（320×240）——
   那是给人脸的缩略图。但 `backend_apple.py` 文件头的性能实测（手部 4.8ms）
   本身是在 **640×480** 上测的，即设计意图就是 640。手在 320 宽画面里只有
   几十像素，指关节间距个位数，没有可判别结构。
   → 新增 `VISION_W=640`，**只有 Vision 这一路**用高分辨率，人脸仍走 `DETECT_W=320`。
2. **退避死锁**：连续检测不到会退避到每 12 帧（≈0.4s），而 `get_vision()`
   把超过 `VISION_STALE_AFTER(0.35s)` 未重新推理的帧判为过期、按没检测到返回
   —— 越退避越过期，永远回不来。→ 退避上限降到 4 帧（`VISION_BACKOFF_MAX`）。
   **教训：任何"退避"上限都必须快于对应的过期判定，否则就是自锁。**
3. **兜底从未接上**：`HandBackendSkin`（肤色+轮廓，无模型依赖）早已实现，
   但 `MotionTracker` 从来没实例化过它 → Vision 一失败就毫无后备。
   → Vision 手部连续 1.2s（`HANDSKIN_AFTER`）失败即启用肤色方案，`_hand_src` 记录来源。
   坑：人脸框按 320 缩略图坐标算，喂高分辨率画面前**必须换算**，否则会把脸当手。

附带：`min_hand_conf` 0.30→0.20、最少关节 8→6（参数化）；
三个后端 `__init__` 补 `**_kw` —— AutoEngine 会把同一套参数发给所有后端，
后端不能因不认识的参数就构造失败，否则退化链整条断掉（本机只剩 apple/opencv）。

**排查这类"检测不到"问题的顺序**：先确认送检分辨率 → 再查退避/过期这类
自锁参数 → 最后看兜底路径是否真的接上了（而不是仅仅"写了这个类"）。

## 手部轨迹对不上（用户反馈，已修）

症状：手检测到了，但游戏光标轨迹/方向跟手对不上（水果切切完全对不上）。
**这不是检测问题，是"跟错了目标"**。

根因：`MotionTracker._hand_state` 从来没给 `HandState.area` 赋值（默认 0.0），
而 `HandController` 恰恰靠 `max(hands, key=lambda z: z.area)` 选主手 ——
所有手评分相同，`max` 就固定返回**第一个**。Apple Vision 返回多只手时
（另一只手/误检/背景里的手）顺序并不稳定 → 主手每帧在几只手之间瞬移。
证据：area 全 0 时 `[A,B]` 选 A(0.3)、`[B,A]` 选 B(0.8)，纯由顺序决定。

修复：
1. `_hand_state` 用可见关节包围盒面积填充 `area`。
2. 新增 `HandController._pick_main`：主手**跟随上一帧那只**（同一只手相邻帧
   位置必然连续）。仅两种情况改选：上一帧那只消失（距离>0.35）、
   或出现面积悬殊 2.2 倍以上的新手。
3. `apply()` 不再自己重选（否则"坐标跟 A 手、手指状态取 B 手"）。
4. 手真的离开（超 `HAND_LOST_AFTER`）时清空主手记忆。

**通用教训（可复用）**：任何"每帧从多个候选里挑一个"的逻辑，都不能只靠
一个瞬时评分 —— 必须带**连续性/所有权**。本项目头部（FaceTargetSelector）
和手部（_pick_main）踩的是同一个坑，只是表现不同（头部是目标漂移，
手部是轨迹跳变）。另外要警惕"字段没被填默认值 0"导致的伪评分相等：
`max()` 在平分时返回第一个，这种 bug 非常隐蔽。

## 手部链路整体重构（第三轮，用户反馈"基本不可用"）

单点修补不够了 —— 读透数据流后确认手部缺整套"目标管理"层：
1. **主手记忆太短**（旧 HAND_LOST_AFTER=0.6s）：快挥时检测必然闪烁，
   每 0.6s 清空重选 → **挥得越快跟得越错**（切水果核心动作恰是快挥）。
2. **隔帧阶梯**：手部走 15Hz，但 apple 只跑手部请求仅 4.8ms，可每帧。
3. **无跨帧身份**：每帧"一串手+选一个"，闪烁即重选。
4. **边沿残留**：丢失后不清 `_armed`，重捕获握着的手凭空触发捏合。

重构架构（HandController 全量重写）：
- `_HandTrack`：tid 跨帧身份 + 每手独立 One Euro 滤波 + 速率限制。
- `_associate` 贪心最近邻，**双门限** 0.28/0.55：追赶档只在唯一候选时启用 ——
  快挥一步跨 0.3+ 是真实的，单门限会当"新手"另起 track，主手永远停原地。
- **控制权 = 带迟滞的所有权**：挑战者连续 6 帧面积 2.2 倍才夺权；
  闪烁 ≤0.30s 冻结（绝不衰减，同头部语义）；真丢失 1.5s 交还。
- 伪 LOST（HOLD 超时）与真 LOST 都要**完整复位边沿状态（含 _armed）**。
- 纯手部游戏推理间隔 → 每帧（`HAND_VISION_EVERY=1`）。

新增 `tools/test_hands.py`（21 项）。全部 177 项断言 + 渲染 20/20 + 单帧 6.47ms。

**教训**：重构"目标选择"类逻辑时，三类状态要分开管理且各有完整复位路径：
身份（track）、所有权（控制权）、语义动作（边沿如 pinch）。
任何一条路径漏复位，都会在"丢失→重捕获"场景凭空触发。

## 手部第三轮（用户："完全不跟，完全重写吧"）—— 第二版架构

**第一版 ID 跟踪被实测证伪**。决定性证据（test_hands[1] 可复现）：
skin 误检块（脖子/窗帘/木桌，面积 0.06）先建立主手后，真手（面积 0.02）
**永远夺不回控制权** —— 面积夺权规则 2.2 倍对这种对比永远不成立。
锁得越稳，跟得越死。这就是"完全不跟"的根因：我把"防跳变"做成了"锁死"。

第二版三条规则（每条单独可断言）：
1. **最近邻跟随**（无面积权重、无夺权迟滞）；
2. **静止误检降权**：连续 12 帧几乎不动且无 21 点姿态 → +0.50 距离惩罚。
   关键洞察：**最近邻规则对静止目标有系统性偏爱**（静止者离自己永远距离 0），
   这条没有的话钉在墙上的误检块永远赢；
3. HOLD/LOST 沿用头部语义（冻结/清零/完整复位边沿）。

来源分层：skin **永不与 Vision 同帧竞争**，只在 Vision 连续 3s 无手后作
降级坐标源，Vision 恢复立即让位。y 轴链路已审计（Vision `1.0-y` 转换正确）。

**最大的元教训**：这次连续三轮"修复"，每轮都靠推理+合成测试自证通过，
但真机体验越来越差。原因是**合成测试验证的是我自己的假设**，
而不是真实失败模式。以后处理"手感"类问题：
1. 先拿真机诊断数据（hand_probe.py 就是为此写的），再动架构；
2. 任何"防 X"机制都要问一句：X 的对立面（本例：真手）会不会被一起防死；
3. 越简单的规则越可证 —— 三条简单规则好过一套互相制衡的复杂机制。

## 手部第四轮（真机诊断数据到位）—— 终于找到唯一真根因

hand_probe 真机 15 秒数据一锤定音：
- **Vision 21 点检出率 0.0%**（645 帧全零）—— 主路径从未工作过
- skin 检出 98.9%，但全是**钉死在画面左缘 (x≈0) 的静态误检**（贴边色块）
- 用户所有"手检测到了但轨迹不对"的反馈里，Vision 从未参与，一直是 skin 误检独撑

**根因（本机可直接内省验证）**：macOS 27.0 beta（26A428）的 pyobjc 把关节常量
暴露为 **FourCharCode 缩写字符串**（`VNHLKWRI`=Wrist，类型 pyobjc_unicode），
而旧系统是全名 `VNHumanHandPoseObservationJointNameWrist`。`_canon` 按全名后缀
匹配 → 22 个手部关节 + 18 个人体关节**全部**映射失败 → 每只检测到的手都在
`len(joints) < min_hand_joints` 处被**静默丢弃**。body 一样全断（全身模式也没工作过）。

修复：模块加载时从 Vision 模块常量构建 `value→规范名` code 表（常量**名**稳定，
值无论是全名还是缩写码都能建表），_canon 三档查找（code 表 → 全名后缀 → repr 正则）。
本机验证：FourCharCode 21/21、全名 3/3、人体 18/18 全部映射成功。

**最大的教训（比前三轮加起来都重要）**：
1. **"检出率 0"先怀疑"结果被丢弃"，而不是"检测器没检测到"** —— 本例 perform
   一直 ok=True 无报错，丢在解析层。凡是"API 成功但结果为空"的，先查中间层。
2. **依赖 `str(枚举)` 的格式是隐式契约** —— 系统/binding 一升级就断，而且断得
   静默（没有异常，只有数据消失）。跨版本兼容要么查稳定属性，要么自己建映射表。
3. **诊断工具的价值被彻底证明**：四轮盲修不如一份 15 秒真机数据。以后体感/手感
   类问题，第一步永远是 hand_probe / --probe 拿数据，第二步才是动代码。
4. 用户说的"之前的就有问题"完全正确 —— 这个 bug 在 repo 初始就存在，
   只是旧测试全部用合成 FaceState/HandState，绕过了整个 Vision 解析层。
   **测试要覆盖"真实格式的输入"，不能只测"自己构造的输入"。**

## 第五轮：映射修好了 Vision 仍 0% —— 还有第二层断裂

上一轮修完 FourCharCode 映射，真机复测 Vision 手部**仍是 0%**。
教训：**复合故障不会一次暴露完** —— 修完一层必须重新拿数据验证，
不能假设"根因只有一个"。

破案方法（没有摄像头也能做）：用 ImageGen 生成写实手部照片 →
直接喂 Vision 请求 → dump observation 的全部方法。发现：

- **检测本身正常**（perform ok=True，检出 1 只手）
- 但 `recognizedPoints()` 在 macOS 27 上**不存在** —— API 换成了：
  - `availableJointNames()` → 21 个缩写关节名单
  - `recognizedPointForJointName_error_(name, None)` → 逐点取
- 旧代码调不存在的方法 → AttributeError → 被 tracker 的 except 静默吞掉
  → 表现仍是"0%"（**异常吞噬把 API 断裂伪装成了检测失败**）

修复：`_extract_points` 双 API 兼容（新 API 优先，旧 API 回退）。
引擎级端到端验证（生成照片，走完整 infer 路径）：21 关节全通、
连续 30/30 帧检出、张合度/伸指/掌心全正常。

**方法论沉淀**：
1. "API 成功但结果为空" + "异常被吞" = 最阴险的故障组合，
   两者叠加时表象会指向错误方向（检测器背锅）。
2. 无摄像头环境下，**生成写实照片**可以替代真机做 Vision 链路验证。
3. macOS beta 的 pyobjc 暴露形式不可依赖：凡是 str()/方法名，都要探测而非假定。

## 抬头灵敏度第二次调高（用户反馈"还有点低"）

`PITCH_FULL_SCALE` 0.43 → 0.38（历史：0.52 → 0.43 → 0.38，两次都只动满速不动死区）。
按下动作键所需 p_raw：0.27 → 0.233 → 0.212。

**关键联动（这个项目的调参纪律）**：降满速会放大"转头时俯仰读数被顶起"的
耦合量折算键值。0.38 + 旧衰减(0.85/0.70) 时 yaw0.45 耦合键值 0.399，
距 JUMP_ON(0.42) 仅 0.02 —— 必须同步加强衰减到 0.95/0.80，
把耦合压回 0.347/0.123。**调 PITCH 增益必须重新验算 PITCH_YAW_SHRINK**。

已确认的边界行为（非 bug，设计使然）：持续小幅抬头（< NEUTRAL_ADAPT_GATE_P
=0.30）时基线会被自适应学走，"抬住后的第二跳"需要抬得更高 ——
这是防坐姿漂移误触的代价。若用户反馈"抬住后难二连跳"，
方案：给 npitch 的学习加"jump_sig 非零期间不学"的门（现在只挡了已按下的）。

## 意图门修复（"第一次抬头容易、后续非常难触发"）

上一段的预测成真了，实机确认后修复：`_adapt` 加**抬头意图门** ——
`jump_sig > JUMP_INTENT_TH(0.28)` 期间冻结俯仰基线学习。
用**意图**（jump_sig）而非**已按下**（jump）判定：意图比触发更早出现。

**阈值 0.28 是两条互相拉锯的测试逼出来的平衡点**：
- 高于噪声折算（3σ→key 0.21）；
- 高于坐姿偏置 0.16 的折算（key 0.24）—— 第一版取 0.20 误挡了它，
  被 test[23]（小幅偏置要被吸收）当场抓住；
- 低于触发线 0.42 —— 危险带 [0.21, 0.30] 全程有保护。

新增 test_head[24]：固定幅度三连跳全触发 + 基线零漂移 + 反向自愈断言。
**教训：加"防学习"门时，阈值必须同时验算两个方向**——
保护得太狠会把自愈（坐姿漂移吸收）一起关死；
test[23] 和 test[24] 这对反向断言就是专门的守卫。
