## 追加：真机跑通 —— 攻克 macOS 摄像头权限（TCC）

用户要求「直接在本机跑起来」，随即暴露出真正的拦路虎，**此前"未验证项"已全部闭环**。

### 根因（重要，已写入 skill 第 0 节）
- 直接 `python main.py` 时日志只有 `OpenCV: not authorized to capture video (status 0), requesting...`，
  **且完全没有系统授权弹窗**，游戏静默降级到键盘模式。
- 查证：`/Applications/WorkBuddy.app/Contents/Info.plist` **没有** `NSCameraUsageDescription`。
  TCC 把子进程的摄像头申请归到「负责进程」（即 IDE）的签名上，IDE 未声明用途 → 无法弹窗 → 静默拒绝。
- **这是内核级隐私保护**：用户授予"完全访问权限"、关闭沙箱（`dangerouslyDisableSandbox`）**均无效**。

### 解法（两步，都实测验证）
1. 造 `HeadMario.app`：`Info.plist` 声明 `NSCameraUsageDescription`。
2. App 主程序**必须是 Mach-O**，不能是 shell 脚本 —— 脚本 `exec python` 会丢失签名身份，
   TCC 依旧静默拒绝（已实测复现）。改为编译 `launcher.m`（ObjC）：
   先 `[AVCaptureDevice requestAccessForMediaType:]` 申请权限（弹窗出现、署名"头部控制小游戏"），
   拿到授权后再 `execv` 进 python。`codesign --force --deep --sign -` ad-hoc 签名 + `tccutil reset Camera`。

### 实测结果（全部通过）
- `[HeadMario] 用户授权结果：允许` → 授权弹窗正常出现并被允许。
- `run.log` 中 `not authorized` 报错**归零**；进程 CPU **68.9%**（键盘兜底模式仅 15%）→ 摄像头采集+逐帧检测在跑。
- 新增交付：`launcher.m`、`build_app.sh`、`HeadMario.app/`、`run.log`；README 补「为什么必须用 .app」章节。

### 经验
- ad-hoc 签名的 TCC 授权**绑定二进制指纹**，重新编译后失效需重新授权 → 能改外部 `.py` 就别重编。
- `.py` 在 bundle 外，不受 codesign 封印，编辑不会破坏签名（已 `codesign --verify` 确认 valid）。
- App 无终端，python 默认块缓冲 → 入口加 `sys.stdout.reconfigure(line_buffering=True)`。

### 关键工程结论
1. **斜抛飞行时间必须用解析解**：`t = (−vy₀ + √(vy₀² + 2g(y₁−y₀))) / g`。
   用朴素的 `2|vy₀|/g`（只是"回到出发高度"的时间）会让发球**永远挂网**——网球项目调试时踩过。
2. **文字光晕不能用"多次偏移重绘"**：大字号会糊成实心方块（结算页"通关！"完全不可读）。
   改用**降采样再升采样**的模糊近似，字号越大越稳。
3. `♥`（U+2665）在部分 CJK 字库里缺字形 → HUD 生命必须**自绘**（两圆 + 一个三角形）。
4. 粒子若"每颗粒子建一个 Surface"会掉帧 → 改为**批量画进一张可复用的全屏 SRCALPHA 图层**一次性合成（实测 1.02 ms/帧）。
5. 静态大图（看台人浪、草皮条纹、夜空渐变）只在尺寸变化时重建一次并缓存。
6. `launcher.m` 里 stdout/stderr 若各自 `freopen("w")`，两个 FILE* 都从 offset 0 写 → **互相覆盖**，
   启动日志（尤其权限申请结果）会被 python 输出冲掉。已改为只 freopen 一次再 `dup2(fileno(stdout), fileno(stderr))`（下次重建生效）。
7. `build_app.sh` 默认不再 `tccutil reset`：重编译本身就换签名指纹会重新弹窗，只在排查授权卡死时用 `RESET_TCC=1`。

## v2 重构（16:50 起）：跨平台视觉层 + 全身骨骼

### 用户反馈驱动的方向修正
用户提出四点：①用主流工业级 SOTA 方案；②这是 M4 Mac，可针对优化；
③建模太烂，要上网找高清素材；④四川文化命名很好，要多加文旅元素。
随后追加：**要考虑跨平台**（不能只 Mac）、**要全身骨骼点**、**要做真正的体感游戏**。

### 关键结论：架构必须是"统一骨骼规范 + 多后端"
内部规范 = **COCO-17（人体）+ 21 点（手部）**，坐标用图像归一化、左上原点。
各平台用各自最主流的方案，只负责翻译成规范：

| 后端 | 平台 | 加速 | 本机状态 |
|---|---|---|---|
| apple（Apple Vision） | macOS/iOS | ANE | ✓ 可用 |
| mediapipe（BlazePose 33 点） | Win/Linux/Android | TFLite | ✗ SIGABRT |
| onnx（RTMPose） | 全平台 | CoreML/DirectML/CUDA | 代码就绪，缺模型 |
| opencv | 兜底 | CPU | ✓ 可用 |

### Apple Vision 实测（M4，macOS 27，640×480）
- 手部单独 **4.8ms**；人体单独 8.3ms；**人体+手部 8.3ms**（共享一次推理）
- **人体+手部+人脸矩形 19.7ms** ← 人脸请求会打乱 ANE 调度，坚决不要塞进去
- numpy→CGImage 转换仅 0.17ms，不是瓶颈
- ⚠ 以上是**空白图**的数据；**真实图像上要 16~29ms**（纯色图走了快速路径）

### "加了手之后精度完全下降"的根因（三个叠加）
1. **两个真 bug 让手部几乎完全失效**：
   - `cv2.fitEllipse(cnt)[1]` 取错下标（[1] 是 `(size, angle)` 二元组，角度是 [2]），
     解包抛 **ValueError** —— 而外层只 catch 了 `cv2.error`，异常一路上抛被采集线程
     的 `except Exception` 吞掉。结果是"画面里只要有肤色候选，手部结果永远是空"。
   - `HandController` 的 pinch 边沿检测用错标志位：`_closed_frames == 2 and not
     _was_closed`，而 `_was_closed` 在前一帧已经置 True → 捏合一次都不会触发。
     应该用独立的 `_pinch_fired`。
2. **平滑用了"每帧系数"而非时间常数**：`axis += 0.35*(raw-axis)` 在 30fps 下等效
   95ms 时间常数，帧率掉到 15fps 就变 190ms，手感直接发钝。
   改成 `k = 1 - exp(-dt/tau)` 后帧率变化不再影响跟随速度。
3. **开销叠加把采集线程压到 21~30fps**：Vision 20ms + YuNet 8ms + 960×720 采集。

### 治本方案：按需 + 自适应负载
- `shell` 按游戏 `REQUIRES` 切换 `vision_mode`：`off / hand / body / full`
  —— 12 款纯头部游戏**完全不启动姿态模型**，CPU 从 90~110% 降回 **77%**
- 连续 5 次检测不到目标则把间隔退避到 1/12 帧，检测到立刻恢复高频
  （坐着只露头的人不会白白烧 CPU）
- 摄像头分辨率 960×720 → 640×480（检测本来就在 320 宽上做）

### 反直觉的发现：人体姿态模型对"坐姿只露头"不友好
`VNDetectHumanBodyPoseRequest` 需要看到足够多的身体部位才出结果，
真机 probe 显示坐姿下**返回 0 点**。所以不能拿它当头部控制主信号。
最终分工：**YuNet 每帧出头部（只要脸在就稳）+ Vision 降频出全身与手部**。

### 新增的真机诊断能力（很关键）
- `main.py --probe`：跑 20 秒，每秒打印 cam帧率/脸✓/人体点数/手数/各环节耗时
- `main.py --list-backends`：打印各后端在本机的可用性
- `launcher.m` 支持从 `run_args.txt` 读启动参数（.app 无法从 Finder 传参）
- 沙箱截不到真机画面时，这套日志就是唯一的验证手段

- 原图存 `assets/sprites/_raw/`（JPEG q94，14MB → 3.8MB），可重跑抠底

### 抠底的关键结论（这是本轮最有价值的技术产出）
**连通域才是关键，不是阈值。** 主体内部有大量近白色区域（熊猫白毛、青白瓷、
脸谱白纹样），按亮度抠会抠穿成空洞。正确做法：
1. 四边估背景 → 低分辨率 inpaint 出「背景色场」（兼容渐变背景）
2. 距离够近的算疑似背景，**只保留与画布边缘相连的那片**才是真背景
   → 内部白毛被粗描边封闭、与边缘不连通，因此保留（内部空洞率 0.00%）
3. 二值前景 + 仅轮廓处羽化 1~2px

**反例（踩过）**：用"距离越近越透明"的宽软过渡（lo=9/hi=46）时，
AI 背景自带的细噪点把整片背景拉成 20~40% 不透明度灰雾，主体外一圈脏边且裁不掉。
半透明占比从 30% 降到 0.5~2% 才是对的。

### 三个真 bug
1. `surfarray.blit_array()` 会写掉 alpha → 每个精灵背后多一个黑矩形。
   改用 `pixels3d()` 视图原地写。**做色相旋转时必须注意**。
2. `games/fishing.py` 把地标画到尚未赋值的 `self._bg` 上，直接 AttributeError。
   **上一轮加四川地标时引入，20 款游戏从没跑通过 fishing** —— 截图工具那份
   grep 输出让我误以为通过了，是个教训：批量验证要看逐项结果，不能只 grep"完成"。
3. `Rect.bottom` 是标量不是点，`get_rect(bottom=(x,y))` 抛 invalid rect assignment。

### 其它

## 修「没有识别到头的时候别乱动」（用户反馈）

### 这不是一个 bug，是五处同源问题
都属同一类：**当前没有有效检测，却仍然产生了控制量**。

1. **丢失是逐帧布尔 + 衰减归零**（核心）
   旧实现把"这一帧没检测到"直接当丢失，并把横向量按 0.14s 时间常数衰减到 0。
   单帧漏检很常见（转头/遮挡/曝光突变），于是每次漏检角色往中间滑一下、
   下一帧回来又弹回去 → 这就是用户看到的"乱动"。
   改成三段状态机：TRACKING / HOLD（≤0.15s 冻结，一点不变）/ LOST（立即归零，不衰减）。
   实测闪烁 60 帧后横向量最大偏移从 ≈1.00 降到 0.00000。
2. **人脸框无合理性校验** → 墙上图案/反光被判成脸、中心贴边，归一化后
   axis 直接打满，角色瞬间被甩到一边。加最小尺寸/宽高比/面积/边缘距离筛选。
   原则：**宁可漏检** —— 漏检走冻结/归零，是安全的失败方向。
3. **action 的手臂分支没按来源门控** → 姿态模型隔帧跑还会退避，
   陈旧的 arm_l 让角色在没人做动作时继续"按键"。改为要求 body_found。
   （这条是单元测试抓出来的，我自己写第一版时漏了 hands_up 那一支。）
4. **get_vision() 会一直交出上一帧** → 退避期间 found=True 与抬臂数值一起陈旧。
   加新鲜度门（>0.35s 按"什么都没检测到"返回）。
5. **大厅 dwell 自动确认不检查识别状态** → **人走开了大厅还会自己翻页、
   自己进游戏**。这是最容易被当成"乱动"的一处。
   另：手部丢检后重新捕获，手一直握着也会误触发一次捏合（没有"张开→握拢"转变）。

另加 REACQ_STEP=0.62 限制重新捕获那一帧的跳变（假阳性只出现一两帧就不会甩飞角色）。

### 顺带抓到一个潜伏崩溃
`HandController` 引用不存在的 `C.SMOOTH_TAU`（把"每帧系数"改成时间常数
`HAND_TAU` 时漏改这一处）。它**只在"检测到手"那条分支执行**，所以平时完全看不出来
—— 一检测到手就 AttributeError 崩。教训：**改配置项名字必须全局搜引用**。
现在由 `tools/test_input.py` 第 7 项静态守着（扫 core/ 与 games/ 全部 C.XXX 引用，
当前 216 处全部有效）。

### 验证方式（这类"手感"问题必须用行为断言，不能靠感觉）
- 新增 `tools/test_input.py`：24 项断言，24/24 通过
  （冻结/归零/闪烁/重捕获限速/动作门控/手势误触/大厅自动进入/配置引用）

- 回归：20/20 渲染通过，最慢中位 8.41ms（预算 16.7ms）
